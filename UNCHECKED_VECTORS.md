## 1. Синтез куба (Cube Synthesis)

### Описание
Система создания/синтеза кубов (`CubeSynthesis`) упоминается в коде, но **не прошла тестирование**.

### Найденные классы (обфусцированы):
```
TaskbarHero.EasySaveData.CubeLevelSaveData::.ctor
TaskbarHero.EasySaveData.CubeRecipeSaveData::.ctor
TaskbarHero.Log.CubeSynthesisLog::khw
TaskbarHero.UI.CubeSlotSetter::lag
TaskbarHero.UI.CubeSynthesisAutoFillButton::kxq
```

### Потенциальные уязвимости:
1. **Отсутствие валидации рецептов** — возможность создавать кубы с некорректными ингредиентами
2. **Отсутствие проверки уровня синтеза** — может быть можно скочить через уровни
3. **Защита `ObscuredInt`** — если используется, может быть уязвима как F-08
4. **Серверная синхронизация** — синтез может быть локальным и отправляться на сервер без валидации

### Методика проверки:
- Найти структуру `CubeRecipeSaveData` в памяти
- Модифицировать `cost` рецепта на **отрицательное значение**
- Модифицировать требуемый уровень синтеза на нулевой
- Проверить, сохраняется ли на сервере после автосейва
- Попытаться создать куб с **чужих ингредиентов** (правка `itemId`)

**Риск:** Если синтез не защищён — **HIGH** (как F-01 и F-02)

## 2. Подмена сетевого трафика (Network Hijacking)

### Описание
Пароль шифрования ES3 скомпрометирован (F-06), ключи известны. Это позволяет:
- Расшифровать сохранения
- **Перешифровать с подменёнными данными**
- Отправить на сервер под видом легитимного сейва

### Известные данные (F-06):
```
salt = IV = первые 16 байт файла
key = PBKDF2-HMAC-SHA1(password, salt, 100 итераций, 16 байт)
cipher = AES-128-CBC + PKCS#7
```

### Потенциальные атаки:

#### 2.1. Перехват и подмена сейва целиком
```python
# Перечитать сейв → расшифровать → модифицировать → перешифровать → закидывает в папку
# Сервер проверит подпись? Проверит ли по-новой?
```

**Вопрос:** После F-06 серверная проверка целостности сейва могла быть усилена (как в финале FINDINGS), но неизвестно:
- Проверяет ли сервер **подпись** файла или только **структуру**?
- Есть ли **контрольная сумма** всего архива?

#### 2.2. Подмена einzelных полей через расшифровку-переш кодировку
Если защита целостности работает на уровне файла, но не на уровне полей — можно:
1. Расшифровать сейв
2. Найти конкретное поле (напр. `HeroExp`)
3. Переш cifровать только его
4. Остальное оставить как есть
5. Переш cifровать весь файл

**Риск:** CRITICAL если серверная проверка целостности недостаточна

### Методика проверки:
1. Взять рабочий сейв
2. Расшифровать его полностью (алгоритм из F-06 известен)
3. Модифицировать **одно поле** (напр. `maxCompletedStage`)
4. Переш cifровать файл тем же паролем и солью
5. Заменить оригинальный файл
6. Запустить игру
7. Проверить, **откатился ли сервер** или **принял**

## 3. Редкие кейсы (Rare Box Rolls)

### Описание
F-07 доказал, что содержимое сундуков известно **заранее** и хранится в памяти. Но это не попытка **изменить** редкость выпадения.

### Найденные классы:
```
TaskbarHero.CubeInData::jns
TaskbarHero.BoxData::get_RewardItemId
TaskbarHero.BoxData::get_RewardItemUniqueID
TaskbarHero.Log.BoxOpenLog::.ctor
```

### Потенциальные уязвимости:

#### 3.1. Подмена типа рарности кейса
Если `BoxData.tип` хранит рарность (`910651` — обычный, `920651` — редкий), возможно:
- Изменить тип с `910651` на `920651` (обычный → редкий)
- Перезаписать `RewardItemId` на ID редкого предмета
- Проверить, пережил ли рестарт

#### 3.2. Подмена индекса в очереди
Если очередь в памяти — `BoxData[i]`, то:
- Скопировать данные из одного сундука в другой
- Изменить индекс доступа
- Открыть «свой» редкий сундук вместо полученного обычного

#### 3.3. Взлом RNG (Random Number Generator)
Если сервер использует **seeded RNG**, а seed передаётся клиенту (даже in сейве):
- Предсказать всю цепочку выпадений
- Генерировать сундуки с **гарантированной редкостью**

### Методика проверки:
1. Найти `BoxData` в памяти (известно из F-07)
2. **Изменить `тип` на редкий** (920651)
3. **Изменить `RewardItemId`** на редкий предмет (ID > 500000)
4. Дождаться автосейва
5. Открыть сундук → проверить награду
6. Перезагрузить → проверить, сохранилась ли редкая награда

**Риск:** HIGH — если редкость не проверяется серверо

## 4. Шанс выпадения предметов (Drop Probability)

### Описание
Вероятностный компонент дропа предметов из сундуков и боёв не был проверен.

### Потенциальные уязвимости:

#### 4.1. Таблица весов (если локальная)
Если игра хранит таблицу шансов выпадения локально:
```
rarity_weights = [
  {id: 110001, weight: 0.7},  // обычный
  {id: 110002, weight: 0.25}, // редкий
  {id: 110003, weight: 0.05}  // эпический
]
```
Можно изменить веса: `110002: 1.0` → 100% редкие предметы

#### 4.2. Перехват RNG
Если дроп зависит от `Random.Next()` или `UnityEngine.Random`:
- Переш cifровать сейв с известным seed
- Гарантировать нужный дроп

#### 4.3. Подмена ID в момент присвоения
Как в F-08, перехватить `get_RewardItemId` и подменить значение на выходе.

### Методика проверки:
1. Найти таблицу весов в памяти (поиск по дробным значениям 0.7, 0.25, 0.05)
2. Изменить **все веса на 1.0 для редких** и 0 для обычных
3. Открыть много сундуков → все должны быть редкими
4. Проверить, откатился ли сервер или остались

   - Требует больше работы с памятью

## Приложение: Известные данные для атак

### F-06 (Crypto)
```
Пароль: [СНЯТО в рантайме]
Алгоритм: PBKDF2-HMAC-SHA1(пароль, salt, 100, 16)
Шифр: AES-128-CBC + PKCS#7
Salt = IV = файл[0:16]
```

### F-07 (Box Queue)
```
Пример открытого сундука:
BoxData @ 0x2b045738ab0
  ItemId (защ): 12030
  RewardItemId (защ): 110004
  Type: 910651 (обычный) / 920651 (редкий)
```

### F-08 (Obscured)
```
Формула расшифровки:
значение = ((шифротекст − ключ) ^ ключ)

Защищённые поля:
+0x00  контрольная сумма
+0x04  (ключ ^ значение) + ключ
+0x08  ключ
+0x0C  открытая копия-приманка
```
