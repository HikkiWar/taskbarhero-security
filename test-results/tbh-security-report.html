Security Vulnerability Report · Responsible Disclosure

Rewards are validated by value, never by rate

Two save collections accept unvalidated client values, and one unprotected price table lets a rune upgrade pay the player instead of charging them. Everything else we attacked was correctly rejected — which is what makes the remaining gap precise rather than systemic.

The core issue

What the server never sees

Your protection works on what a value is, not on how fast it arrived. Writing gold, experience or stage progress directly is rejected every time — we tried, and the server restored the true value in all cases.

But a client whose damage has been multiplied kills far faster than the game intends, and every reward that follows is issued by your own code through the normal path. The server sees a stream of individually valid grants and accepts all of them.

Measured on a live account over roughly forty minutes, with only in-memory combat values changed and no save file touched:

None of these were written by us. Every one was credited by the game itself and persisted through restart and synchronisation. This is the vector to close: a server-side sanity check on the rate of experience, gold and stage progression would have caught all of it, and no per-value check ever will.

Method

How the attack was carried out

Recovering the save password

Static extraction is not viable — the build is IL2CPP with GUPS.Obfuscator, so string literals are encrypted at compile time. The password was taken at runtime instead:

  1. Enumerated the constructors of System.Security.Cryptography.Rfc2898DeriveBytes through the exported IL2CPP API (il2cpp_class_from_name, il2cpp_class_get_methods), reading each method's native entry point.
  2. Wrote 0xCC at each entry point and caught the traps in a vectored exception handler, re-arming through single-step so repeated calls were all seen.
  3. Read the arguments at the moment of the call: RDX held the password string, R8 the salt array.
  4. Decoded the managed string. The first attempt read length at +0x14 and rejected the value; the correct layout is length at +0x10 and UTF-16 characters at +0x14.

The recovered password is a fixed constant — identical across sessions, and the same on a second installation.

Deriving the encryption scheme

The hook also gave the PBKDF2 parameters (100 iterations, SHA-1, 16-byte key). Only the salt source was unknown, so nine candidates were tried against the file — the password as UTF-16, various digests, the captured salt buffers. The one that produced valid JSON was the file itself: 

salt = IV = first 16 bytes of the file      (one value, both roles)
key    = PBKDF2-HMAC-SHA1(password, salt, iterations=100, dkLen=16)
cipher = AES-128-CBC + PKCS#7
file   = [salt/IV : 16 bytes][ciphertext]

password = "emuMqG3b…[withheld, 22 chars]"

Confirmed by re-encrypting an unmodified payload with a fresh random salt: the client accepted it silently, proving the scheme was fully reproduced.

One detail matters for reproduction: the plaintext must be re-serialised byte-exactly. ES3 writes CRLF line endings, tab indentation and spaces around colons; any deviation trips the integrity check. Our serialiser round-trips the real save byte-for-byte across 273 308 bytes.

Why file editing was abandoned

Editing the decrypted save is detected correctly — the client warns and restores authoritative data. That control works. It is also irrelevant, because patching the same values in process memory instead makes the client serialise them itself on its next autosave, with no warning and no rollback. The file-level integrity check therefore protects nothing that the client is authoritative over.

All subsequent findings use only ReadProcessMemory and WriteProcessMemory against a running client. No injected library, no hooking, no debugger.

F-01

A negative price makes the upgrade pay the player

High
Impact
Unlimited gold, credited through the normal transaction path.
Persistence
Survives restart and synchronisation.
Status
Confirmed on a live account

The rune upgrade cost table sits in ordinary read/write memory with no protection: 672 rows, stride 0x50, each <RuneKey><Level><currencyKey><cost>. Writing a negative cost inverts the transaction — upgrading a rune adds gold instead of removing it.

This is the most serious finding precisely because the gold does not arrive by a forged write. It is granted by your own purchase code, enters the protected store as legitimately earned, and survives everything. Direct writes to the same balance are rejected; this path is not.

The price table resets on restart, but the gold does not. Re-applying takes one write, so the cycle is unbounded.

F-04

Combat stats and the experience multiplier are freely writable

Medium
Impact
Arbitrary damage, survivability and experience gain for the session.
Persistence
Values reset on restart — the rewards they produce do not.
Status
Confirmed

The computed combat profile is a float array with 0x10 stride. One anchor gives access to the whole set, and the same structure is used for enemies — mob health is reachable the same way and can be set to 1. 

-0x40  attack damage      -0x30  attack speed
-0x20  crit chance        -0x10  crit damage
 0x00  MAX HP             +0x10  defence

+0x2A0  experience multiplier   (1.0 = normal 100%)
+0x2B0  additional experience
+0x350  HP per kill

Setting +0x2A0 to 50 000 makes a single kill award tens of thousands of experience. As with F-01, the experience is granted by your own code and is therefore kept — direct writes to HeroExp are rejected, this path is not.

None of these values exist in the save file; they are recomputed from attributes and equipment at load. That is why a restart clears them, and why fixing only the persistent findings would move this vector rather than remove it.

F-05

Attribute levels may exceed the ability-point budget

Medium

No invariant ties spent levels to earned points. In one test the sum of a hero's attribute levels was driven 53 above AllocatedHeroAbilityPoint and accepted silently. A minimal case was reproduced with the hero at AbilityPoint = 0: a node raised from 0 to 1 gave sum = 23 against a budget of 22, and was saved without complaint.

This is the cheapest fix in the report and is independent of F-02.

F-06

Save encryption uses a static password

Info

Method and formula are given above. Listed as informational because it is not what enables the other findings — file edits are correctly detected and rolled back. It matters because one recovered constant removes any confidentiality expectation for every player's save.

The full password is withheld from this page and will be supplied directly in the private disclosure message.

F-02 — permanent attribute change

import ctypes, struct

def find_attribute(proc, key):
    """Objects are identified by header, not by address: a valid klass
    pointer at -0x10 and a zero monitor at -0x08 separate real instances
    from the static tables that also contain the key."""
    needle, hits = struct.pack("<i", key), []
    for base, size in committed_rw_regions(proc):
        data = read(proc, base, size)
        off = data.find(needle)
        while off != -1:
            klass, monitor = struct.unpack_from("<QQ", data, off - 0x10)
            if klass > 0x10000000000 and monitor == 0:
                hits.append(base + off + 4)        # address of Level
            off = data.find(needle, off + 1)
    return hits

for addr in find_attribute(proc, 101002):          # 101002 = hero 101 HP node
    write_i32(proc, addr, 58)                      # was 8

# wait for the client's own autosave (~3 min), then relaunch.
# The value is present in the save and survives synchronisation.

Note what makes F-01 and F-04 different in kind from F-02. They never write a protected value at all — they change an input to your own reward logic and let it do the crediting. No integrity check on the stored value can see this.

Control group

What already works

These were attacked with the same method and effort as the findings above, and your existing protection defeated all of them. On save, the client rebuilds the record from a protected store and serialises that — a freshly allocated object holding the true value appeared every time, while the patched copies were ignored. Remediation

How to close each vector

1 · Sign-check every transaction closes F-01

The cheapest and most urgent fix. A purchase must never be able to increase the player's balance: 

cost = price_table[rune_key][level]        // server-side table, not the client's
assert cost > 0                            // a purchase cannot pay the player
assert player.gold >= cost
player.gold -= cost

The price must come from the server's own table. Accepting a client-supplied cost is what makes the negative value possible in the first place.

2 · Validate the rate, not just the value closes F-04

This is the finding no per-value check can reach, because every individual grant is genuine. Progression has physical ceilings — derive them from your own balance data and reject or flag anything far beyond: 

// per account, sliding window
exp_gained   / elapsed  <=  max_exp_per_second(stage, party)   * tolerance
gold_gained  / elapsed  <=  max_gold_per_second(stage)         * tolerance
stages_cleared / elapsed <= max_stage_rate(player_power)        * tolerance

A tolerance of 3–5× absorbs legitimate variance from equipment and buffs. The run documented in this report exceeded any plausible ceiling by orders of magnitude — 99 stages and roughly two million experience in forty minutes — and would have been caught immediately by even a loose bound.

Rate checks also cover future variants of the same trick. Whatever an attacker accelerates — damage, attack speed, mob health, drop rates — the observable outcome is always an impossible reward rate.

3 · Turn the price into a tripwire detects, not just blocks

A sharper variant of fix 1, worth considering instead of a plain rejection. Let the client keep sending the price it believes it paid, and compare that field against the server's own table on every purchase. A mismatch is not an anomaly to weigh — it is proof that the process memory was modified. 

// client already knows the price; make it part of the request
POST /rune/upgrade  { rune_key, level, client_price }

server:
  real = price_table[rune_key][level]
  if client_price != real:
       flag_account(reason="price_mismatch",
                    expected=real, reported=client_price)
       // no legitimate client can produce this
  charge(real)                       // always charge the real price

Why this is stronger than blocking outright:

  • No false positives. Unlike the rate checks in fix 2, which need a tolerance band for equipment and buffs, a price mismatch has no innocent explanation — an unmodified client cannot generate one.
  • It identifies the account, not just the attempt. A rejected transaction tells you nothing about who tried; a mismatch report names them.
  • It does not teach the attacker what you fixed. If the edit visibly stops working, they move on and look for the next unprotected table — quietly. If it appears to work, the signal keeps arriving.

The same pattern generalises: any value the client computes from a table you also hold can be echoed back and compared. Damage per hit, experience per kill and drop rolls are all candidates — each one turns a silent memory edit into a signed confession. Pair it with a deliberate response policy (flag and review rather than instant ban) so a corrupted install or a stale build does not punish an honest player.

4 · Extend protected storage closes F-02, F-03

Apply the mechanism already guarding currency, items, experience, ability points and stage progress to attributeSaveDatas and RuneSaveData. These two collections are the only ones without it, and the code already exists.

Add the accompanying server-side invariants, which hold regardless of how the client stores the values: 

Σ attributeSaveDatas[hero].Level  ≤  AllocatedHeroAbilityPoint[hero]
AllocatedHeroAbilityPoint[hero]   ≤  points_for_level(HeroLevel[hero])
Σ rune_upgrade_cost(rune, level)  ≤  currency actually spent by this account

5 · Reduce the value of a modified client

Combat stats (F-04) live only in memory and cannot be protected by storage checks — a determined attacker will always be able to edit them. Treat that as given and make it unprofitable instead: the rate checks above turn an accelerated client into a flagged account rather than a rich one.

We deliberately do not recommend client-side anti-tamper or anti-debug hardening as a primary control. This engagement is itself the argument: the save-file integrity check is well built and was bypassed in minutes by editing memory instead of the file. Client-side checks raise cost; only server-side validation changes the outcome.

6 · Rotate the save password closes F-06

Treat the current constant as public. Deriving the key per account — for example from the account identifier plus a server-issued secret — means one recovered value no longer opens every player's save.

Scope

Method, environment and limits

All work was local: the reporter's own account, own save file, own client. Attribute and rune changes were reverted after verification, and a full comparison against a pre-test backup confirmed no equipment, hero level, pet or item was lost or altered. The progression figures in the first section were left in place as evidence and can be rolled back on request.

  • User-mode memory reads and writes only. No injected library, no debugger, no modified binary.
  • No attempt was made to have the server mint or duplicate any tradeable item, and no production server logic was attacked. Item findings are limited to observing that existing validation correctly rejects client-side changes.
  • Not located: the static table holding base equipment stats, and per-stage gold-drop values. Both are expected to share the exposure of F-04 but this was not verified and should not be read as confirmed.
  • An earlier hypothesis that a particular structure held combat damage was withdrawn — it was the TextMeshPro glyph table.
